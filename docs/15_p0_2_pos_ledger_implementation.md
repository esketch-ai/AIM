## 0. 이번 스텝이 해결한 것

P0-1(절기·일출·일몰)이 끝나고 문서 12 §6이 남긴 P0 성공 기준은 두 개였습니다.

```
② 정산 CSV 1건 업로드 → SalesLedgerFact 1건 생성 → 유휴율 계산
③ 기존 28개 테스트 전부 통과 (회귀 0)
```

이번 스텝에서 이 기준이 **처음으로 충족**되었습니다. 그 전까지 유휴율·객단가는
테스트베드 JSON에 박혀 있는 하드코딩 값이었고(`TENANT_001`의 0.35 / 24,000원),
그 값이 그대로 전략 엔진의 매출 추정으로 흘러 "예상 +240,000원"가 화면에 나왔습니다.
즉 **근거 없는 숫자가 금전적 약속으로 제시되던 상태**였습니다.

## 2. 핵심 설계 판단: 정원이 없으면 실패한다

### 2.1 문제

유휴율은 다음 식입니다.

```
유휴율 = (정원 − 실 결제건수) / 정원
```

POS 매출 파일에는 **분자(결제건수)**가 있으나 **분모(정원)**는 없습니다.
그럼에도 기존 코드는 유휴율을 0.35 같은 상수로 갖고 있었습니다.

### 2.2 선택지 3개와 판정

| 선택지 | 판정 |
| :--- | :--- |
| ① 업종별 평균 정원을 가정해 계산 | ❌ **기각**. 업종·매장마다 정원이 다르며, 이건 추정치가 아니라 꾸며낸 숫자입니다. 문서 12 §7 총괄자 언견("그 숫자를 지탱하는 데이터가 모의값이면 6D 초정밀 지능이라는 이름은 그 자체로 사기입니다")에 정면으로 어긋납니다. |
| ② 정원을 모르면 유휴율만 `None` 처리 | ⚠️ 부분 채택. 개별 필드는 정직하지만, 파이프라인은 여전히 "정산 파일을 받았습니다"라고 말하게 됩니다. 사장님은 무엇이 안 됐는지 모릅니다. |
| ③ **정원 컬럼을 필수로 요구하고, 없으면 422로 거절** | ✅ **채택**. 실패 이유가 명시적이고, 감사 장부에 남으며, 사장님이 무엇을 고쳐야 하는지 알 수 있습니다. |

### 2.3 실측 결과

```
POST /api/v1/tenant/TENANT_001/pos-ledger  (정원 컬럼 누락 파일)
→ HTTP 422
{
  "status": "COLLECTION_FAILED",
  "collection": {
    "status": "FAILED",
    "failure_reason": "필수 컬럼을 찾지 못했습니다: capacity_units. 인식된 헤더: 영업일, 시간대, 결제건수, 매출액",
    "evidence_tier": "C_ILLUSTRATIVE"
  },
  "message": "정산 파일을 계산하지 못했습니다. 유휴율은 '(정원 - 실 결제건수) / 정원'이라 정원 컬럼이 반드시 있어야 합니다. 확인 후 다시 올려 주세요."
}
```

정원이 0인 행도 같은 취급입니다. **`0석 = 100% 만석`이 아니라 `계산 불가`**입니다.

```
영업일,시간대,결제건수,매출액,테이블수
2026-10-06,14:00,0,0,0
→ FAILED: "2행: 정원(0)이 0 이하라 유휴율 산출 불가"
```

## 3. 실측이 전략 엔진까지 흐르는 경로

파서가 숫자를 뽑아내는 것만으로는 제품 가치가 생기지 않습니다.
전략 엔진이 실제로 읽는 필드는 `BusinessState.idle_capacity_rate`와 `unit_price`입니다.

```
SalesLedgerFact.idle_capacity_rate
        │  apply_to_business_state()  ← model_copy (원본 불변)
        ▼
BusinessState.idle_capacity_rate / unit_price
        │
        ▼
FnbDomainPlugin.evaluate_triggers() → StrategyObjective.projected_revenue
```

성수 아뜰리에 샘플로 확인한 실측 전후 차이:

| 항목 | 이전(시연값) | 이후(정산 실측) |
| :--- | :---: | :---: |
| 유휴율 | 35.0% | **50.8%** |
| 객단가 | 24,000원 | 24,000원 (실측 일치) |
| 추정 추가 건수 | 10건 | **15건** |
| 예상 추가 매출 | 240,000원 | **360,000원** |

객단가가 하드코딩 값과 **우연히 일치**한 것은 시연값이 그나마 그 매장에 가까웠다는 뜻이지,
하드코딩이 옳았다는 뜻이 아닙니다. 유휴율은 15.8%p 어긋났고 매출 추정은 50% 흔들립니다.

### 3.1 비변형성 방어

`apply_to_business_state()`는 `model_copy(update=...)`로 새 객체를 만듭니다.
테넌트 레지스트리의 원본 상태가 조용히 바뀌면, 그 다음 화면에 나오는 모든 숫자의
출처를 추적할 수 없게 됩니다. 테스트 `test_original_business_state_is_not_mutated`가 이걸 지킵니다.

## 4. 실측값 계산 검증 (샘플 파일 손대조)

`data/sample_pos_ledger.csv` — 성수 아뜰리에, 2026-10-06, 18석, 14개 시간대.

| 시간대 | 결제건수 | 정원 | 유휴율 | 판정 |
| :--- | ---: | ---: | ---: | :--- |
| 08:00 | 2 | 18 | 88.9% | ✅ |
| 12:00 (점심 피크) | 16 | 18 | 11.1% | ✅ |
| **15:00** | **3** | **18** | **83.3%** | ✅ 타임어택 트리거 구간 |
| **19:00** | **17** | **18** | **5.6%** | ✅ 저녁 피크 |
| 일 합계 | 124 | — | 평균 50.8% | ✅ |

- 매출 합계 `2,976,000원` — 14행 직접 합산과 일치
- 객단가 `2,976,000 ÷ 124 = 24,000원` — 정확히 정수
- 재고부족품목 `["통밀사워도우", "라벤더라떼"]` — 3행 중복 제거 확인

실제 파일의 표는 `18석 × 14시간`이므로 이 유휴율은 **좌석 시간 기준**입니다.
테이블 회전(2좌석 1시간 = 1시간 차감)이 반영되지 않는 한계는 §7에 남기겠습니다.

## 5. 정직성 회로 (Gate 0)

### 5.1 실패 7종 전수 검증

| 입력 | 결과 |
| :--- | :--- |
| 빈 파일 | FAILED — "업로드된 정산 파일이 비어 있습니다." |
| 헤더만 있는 파일 | FAILED — "정산 데이터 행이 없습니다" |
| 정원 컬럼 누락 | FAILED — "필수 컬럼을 찾지 못했습니다: capacity_units" |
| 정원 0인 행 | FAILED — "정원(0)이 0 이하라 유휴율 산출 불가" |
| 숫자 파싱 불가 (`사십`) | FAILED — "**2행**: 숫자로 읽을 수 없는 값: '사십'" (행 번호 포함) |
| 형식 완전 불일치 (`foo,bar,baz`) | FAILED — 인식된 헤더 3개를 그대로 노출 |
| 깨진 바이너리 | FAILED — "인코딩을 판별할 수 없습니다" |

### 5.2 자기 감사에서 잡은 결함 하나

`_decode()`가 처음에 `latin-1`을 최후 후보로 두었습니다. **latin-1은 모든 바이트를
항상 성공적으로 디코딩**하므로, (a) "인코딩 판별 불가" 실패 분기가 도달 불가능한 죽은 코드이고,
(b) 깨진 바이너리 파일이 mojibake로 통과해 무의미한 오류 메시지를 냅니다.
Gate 0 취지에 어긋나므로 `latin-1`을 제거하고, 이 사실을 재현하는 테스트를 추가했습니다.

### 5.3 부분 실패의 처리

정상 행이 하나라도 있으면 그날의 측정치를 내고, **누락 건수와 사유를 장부에 함께 남깁니다.**
전체를 버리면 사장님 파일 한 줄의 오타를 이유로 어제 매출 전체를 버리게 됩니다.

```
영업일,시간대,결제건수,매출액,테이블수
2026-10-06,14:00,4,96000,18      ← 정상
2026-10-06,15:00,사십,96000,18    ← 깨짐
→ SUCCESS (결제 4건) + failure_reason: "건너뛴 행 1건: 3행: 숫자로 읽을 수 없는 값: '사십'"
```

## 6. 헤더 표기 흡수

국내 POS 업체마다 헤더가 다릅니다. 정규식 대신 **정규화(공백·구분자 제거) 후 별칭 사전**으로
결정적으로 매핑했습니다.

| 정규화 키 | 흡수 표기 (일부) |
| :--- | :--- |
| `business_date` | 영업일 / 결제일 / 매출일 / 거래일 / 일자 / 일자형 |
| `hour` | 시간 / 시간대 / 시각 |
| `transaction_count` | 결제건수 / 거래건수 / 주문건수 / 판매건수 / 건수 |
| `gross_revenue_krw` | 매출액 / 총매출 / 결제금액 / 합계 / 금액 |
| `capacity_units` | 최대수용건수 / 좌석수 / 테이블수 / 정원 / 수용인원 / 가능건수 |
| `low_stock_items` (선택) | 재고부족품목 / 품절품목 |

값 표기도 흡수합니다: `20261006` → `2026-10-06`, `14시` / `14:30` → `14:00`, `"96,000원"` → `96000`.

## 8. 총괄 관리자 결론

> *"이번 스텝은 숫자 하나를 진짜로 만든 스텝입니다. 그 숫자가 매출 약속의 근거가 됐기 때문입니다.*
>
> *이전까지 유휴율 35%는 JSON에 박힌 값이었고, 그 값으로 사장님께 +24만원을 약속했습니다. 누구도 그 35%가 어디서 왔는지 답할 수 없었습니다. 이제 사장님이 자기 정산서를 올리면 14개 시간대에서 직접 계산되고, 그 결과가 **근거 등급 A**로 전략 엔진에 들어갑니다. 예측 24만원이 실측 기반 36만원으로 바뀌었습니다.*
>
> *더 중요한 것은 **실패의 태도**입니다. 정원이 없는 파일을 받았을 때 저희는 422로 거절했습니다. '대략 이 정도 idle이겠지' 하고 숫자를 만들어서 돌려주는 것보다, '정원 컬럼이 없습니다'라고 말하는 게 백 배 낫습니다. 사장님은 그 한 칸만 채워서 다시 올리면 됩니다.*
>
> *다만 한계를 분명히 말합니다. 지금 유휴율은 좌석·시간 단위라 테이블 회전이 반영되지 않습니다. 2인 테이블이 시간당 두 번 팔리는 매장에서는 실제보다 낮게 나옵니다. 이건 다음 스텝에서 좌석 단위 원시 데이터를 받을 때 해결합니다. **지금 이 한계를 모른 채 숫자를 보여주는 것**이 우리가 경계하는 바로 그 사고입니다."*
